## Ratified controller decisions (Mike, 2026-08-24)

1. **HO-1 (hex alignment): FIX to +π/6 radians; the option's default stays ON.** The H5OINA Euler data is radians; the alignment to the EDAX/DREAM3D hexagonal X-axis standard is +30°, which in the data's unit is π/6. (Today's code adds the literal `30.0F` — thirty *radians* — to radian data.)
2. **HO-6 (EbsdLib H5OinaReader): FIX ON `topic/3_1_1_staging`.** (a) LatticeConstants γ slot must store `ang[2]`, not a duplicate of β; (b) H5OINA stores lattice angles in radians (correct per the file format) — EbsdLib converts them to **degrees** on import so LatticeConstants is consistent with the Ang/Ctf importers. Also fix the unchecked reads at the same site. NX-side test data / assertions updated accordingly.
3. **HO-4/HO-5 (pattern data): DESCOPE.** Keep the parameter; make the preflight failure an honest "pattern import is not yet supported for H5OINA files" error; fix the latent uint16/uint8 + offset inconsistencies behind it (or excise the dead execute block); document as a known limitation.
4. **Archive disposition:** keep `H5Oina_Test_Data.tar.gz` and its genuine AZtec `.h5oina` (irreplaceable realism); **stop comparing against the NX-generated `.dream3d` exemplar** (self-oracle; it also bakes in HO-6's radians). Replace with Class 2 assertions whose expected values come from the independent h5py readback of the `.h5oina` itself. No new archive upload.
5. **HO-9 (`stackingOrder` accepted-but-unused):** implement it if the fix is contained to this filter's files; otherwise document + guard (warning) and log follow-up. Implementer proposes, gate arbitrates.
